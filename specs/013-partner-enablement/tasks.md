## Dependencies and implementation strategy

Setup T001–T003 → Foundation T004–T009 → US1 T010–T016 → US2 T017–T027 → US3 T028–T038 → Acceptance T039–T048.

- US1 is the MVP: demonstrate authorized assigned work and existing-domain links before adding guides. This is a validation checkpoint, not authorization to stop the full feature or deploy it.
- US2 domain tests can use accepted-plan fixtures without the workspace; its final UI integrates the US1 shell/revalidation. US3 tests use exact published-guide fixtures; production implementation relies on US2 policy, source and preview services.
- Within each phase, tests precede implementation, persistence precedes services, services precede adapters/UI, and the story gate follows them. T003's final manifest completeness cannot pass until later files are implemented; use targeted cases for interim development without editing the canonical manifest.
- T022 establishes source policy before T023/T024 exact reviews. T032 requires T030/T031; T034 requires T032/T033; T035 requires those review semantics. T041 follows lifecycle tests and all story state machinery. T046 precedes the complete acceptance capture T047. T048 may document evidence afterward without changing the tested runtime source; any runtime change requires renewed affected checks and complete final evidence.

## Parallel examples

- US1: T010 workspace integration tests and T011 projection sentinel tests touch different files after foundation.
- US2: T017 content unit tests, T018 guide lifecycle tests and T019 source race tests may be authored independently after foundation; run database-mutating suites through their owned runner.
- US3: T028 deterministic progress unit tests and T029 learning integration cases use separate files once the guide contract is stable.

Shared `partners.ts`, `commands.ts`, `projection.ts`, manifest, migration and UI integration edits remain sequential. No general cross-story parallel implementation is assumed.
